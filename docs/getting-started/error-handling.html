Error handling

Error handling в AirCMS — это механизм, который перехватывает исключения во время обработки запроса и передаёт их в специальный error controller текущего модуля или контекста.

Что такое Error handling

Когда приложение обрабатывает запрос, AirCMS проходит цепочку: Front → Router → Controller → Action → View/Response. Если на любом из этих этапов выбрасывается Throwable, фреймворк не должен показывать пользователю сырой PHP error. Вместо этого он пытается найти контроллер ошибки и передать туда исходное исключение.

На практике error controller нужен для трёх задач: вернуть аккуратный JSON в API, показать красивую HTML-страницу в UI и записать технические детали ошибки в лог.

Важно: error controller — это обычный controller, но он наследуется от Air\Core\ErrorController. Благодаря этому внутри него доступны getException(), isExceptionEnabled(), getRequest(), getResponse(), getRouter() и getView().

Когда запускается error controller

Error controller запускается, если во время обработки текущего запроса возникло исключение или PHP error, превращённый во внутреннее исключение через error handler.

Routing error

Например, route не найден, controller class не существует или action method отсутствует.

Controller/action error

Исключение выброшено вручную внутри action, service, model, form validation или сторонней интеграции.

View error

Шаблон view/layout не найден или внутри .phtml произошла ошибка.

Model/Form error

Ошибка ORM metadata, query, validation, filter или validator.

Пример action, который выбрасывает исключение
<?php

namespace App\Module\Api\Catalog\Controller;

use Air\Core\Controller;
use App\Model\Property;
use RuntimeException;

class Property extends Controller
{
    public function details(Property $property): array
    {
        if (!$property->enabled) {
            throw new RuntimeException('Property is disabled', 404);
        }

        return $property->toArray();
    }
}

Как AirCMS ищет error controller

AirCMS учитывает текущий модуль и текущий context. Если ошибка произошла внутри context, фреймворк сначала ищет error controller внутри этого context. Если context-level error controller не найден, используется module-level error controller.

Где произошла ошибкаСначала ищетЗатем ищет

Api без contextApp\Module\Api\Controller\Errorесли не найден — исключение может быть проброшено дальше
Ui / BlogApp\Module\Ui\Blog\Controller\ErrorApp\Module\Ui\Controller\Error
AdminApp\Module\Admin\Controller\Errorcore/admin fallback зависит от конфигурации проекта

Module-level error controller

Module-level error controller лежит прямо внутри папки модуля. Такой контроллер обрабатывает ошибки всего модуля, если для конкретного context не создан свой error controller.

app/Module/Api/Controller/Error.php
<?php

declare(strict_types=1);

namespace App\Module\Api\Controller;

use Air\Core\ErrorController;

class Error extends ErrorController
{
    public function index(): array
    {
        $exception = $this->getException();

        $this->getView()->setLayoutEnabled(false);
        $this->getView()->setAutoRender(false);
        $this->getResponse()->setStatusCode(500);

        return [
            'error' => true,
            'message' => $exception?->getMessage(),
        ];
    }
}

Для API почти всегда нужно отключать layout и auto render, потому что error controller обычно возвращает массив, который AirCMS сериализует в JSON.

Context-level error controller

Context-level error controller нужен, когда один context должен иметь собственный формат ошибок. Например, catalog API может возвращать один формат, auth API — другой, а public API — третий.

app/Module/Api/Catalog/Controller/Error.php
<?php

declare(strict_types=1);

namespace App\Module\Api\Catalog\Controller;

use Air\Core\ErrorController;

class Error extends ErrorController
{
    public function index(): array
    {
        $exception = $this->getException();

        $this->getView()->setLayoutEnabled(false);
        $this->getResponse()->setStatusCode(404);

        return [
            'error' => true,
            'scope' => 'catalog',
            'message' => $exception?->getMessage(),
        ];
    }
}
Когда полезно: context-level error controller удобно использовать для REST API, где разные группы endpoints имеют разные требования к формату ответа.

Доступ к исключению

Внутри error controller исходное исключение доступно через $this->getException(). Метод возвращает Exception, Error или null.

Получение информации об исключении
<?php

$exception = $this->getException();

return [
    'handler' => $exception ? get_class($exception) : null,
    'code' => $exception?->getCode(),
    'message' => $exception?->getMessage(),
    'file' => $exception?->getFile(),
    'line' => $exception?->getLine(),
];

Обычно наружу не стоит отдавать file, line и trace в production. Эти данные лучше писать в лог, а пользователю возвращать безопасное сообщение.

Запись ошибок в Log

AirCMS содержит helper Air\Log. Он пишет записи в built-in log model, если в конфигурации включены логи: logs: true в Config::defaults() и air.logs.enabled после сборки конфига.

Ручная запись ошибки в лог
<?php

namespace App\Module\Api\Controller;

use Air\Core\ErrorController;
use Air\Log;

class Error extends ErrorController
{
    public function index(): array
    {
        $exception = $this->getException();
        $request = $this->getRequest();

        Log::error($exception?->getMessage() ?? 'Unknown exception', [
            'handler' => $exception ? get_class($exception) : null,
            'code' => $exception?->getCode(),
            'ip' => $request->getIp(),
            'user-agent' => $request->getUserAgent(),
            'params' => [
                'get' => $request->getGetAll(),
                'post' => $request->getPostAll(),
            ],
        ]);

        return [
            'error' => true,
        ];
    }
}

Для типового логирования исключений и request params можно использовать Log::requestException().

Короткая запись исключения и request context
<?php

use Air\Log;

$exception = $this->getException();

if ($exception) {
    Log::requestException($exception, $this->getRequest());
}
Безопасность: не записывай в лог пароли, access tokens, payment card data и другие секреты. Если логируешь post, лучше заранее очищать чувствительные поля.

reportErrors и модификация вывода

В Config::defaults() параметр reportErrors влияет на air.exception, display_errors и error_reporting. Внутри error controller можно читать этот флаг и решать, показывать ли подробности исключения.

Отключение подробных ошибок в config.php
<?php

use Air\Config;
use Air\Core\Route;

return Config::defaults(
    project: 'AIR',
    reportErrors: false,

    api: fn() => Config::api(
        domain: 'api.*',
        routes: [
            '/property/:property' => Route::r(
                context: 'catalog',
                controller: 'property',
                action: 'details'
            ),
        ],
    ),
);
Разный вывод для dev/prod
<?php

use Air\Core\Front;

$exception = $this->getException();
$reportErrors = Front::getInstance()->getConfig()['air']['exception'] ?? false;

if ($reportErrors) {
    return [
        'error' => true,
        'handler' => $exception ? get_class($exception) : null,
        'message' => $exception?->getMessage(),
        'trace' => $exception?->getTrace(),
    ];
}

return [
    'error' => true,
    'message' => 'Internal server error',
];

Также ErrorController получает этот режим через setExceptionEnabled(). Проверить его можно методом $this->isExceptionEnabled().

Переопределение status code

Базовый ErrorController::init() пытается поставить HTTP status code из $exception->getCode(). Но на практике код исключения не всегда является валидным HTTP status code. Поэтому в своём error controller лучше явно нормализовать статус.

Нормализация HTTP status code
<?php

use Air\Exception\InvalidInput;
use Air\Exception\NotAllowed;
use Air\Form\Exception\Validation;

$exception = $this->getException();

$statusCode = 500;

if ($exception instanceof Validation) {
    $statusCode = 400;
} elseif ($exception instanceof InvalidInput) {
    $statusCode = 400;
} elseif ($exception instanceof NotAllowed) {
    $statusCode = 403;
} elseif (is_int($exception?->getCode()) && $exception->getCode() >= 400) {
    $statusCode = $exception->getCode();
}

$this->getResponse()->setStatusCode($statusCode);

Ответ можно дополнительно настроить через $this->getResponse(): установить status message, headers или body.

Form validation errors

В AirCMS форма выбрасывает Air\Form\Exception\Validation, когда вызывается validateOfFail() и данные не проходят проверку. В такой ситуации error controller может вернуть список ошибок формы вместо обычного server error.

Название метода: в ядре AirCMS метод называется validateOfFail(). По смыслу это «validate or fail»: провал validation приводит к исключению Air\Form\Exception\Validation.
Action с validateOfFail()
<?php

namespace App\Module\Api\Controller;

use Air\Core\Controller;
use Air\Form\Form;
use Air\Form\Input;

class Contact extends Controller
{
    public function send(): array
    {
        $form = new Form(elements: [
            Input::email('email'),
            Input::textarea('message'),
        ]);

        $data = $form->validateOfFail($this->getParams());

        return [
            'success' => true,
            'data' => $data,
        ];
    }
}
Обработка Air\Form\Exception\Validation
<?php

namespace App\Module\Api\Controller;

use Air\Core\ErrorController;
use Air\Form\Exception\Validation;

class Error extends ErrorController
{
    public function index(): array
    {
        $exception = $this->getException();
        $this->getView()->setLayoutEnabled(false);
        $this->getResponse()->setStatusCode(500);

        if ($exception instanceof Validation) {
            $this->getResponse()->setStatusCode(400);

            return [
                'error' => true,
                'type' => 'validation',
                'fields' => $exception->getForm()->getErrorFields(),
            ];
        }

        return [
            'error' => true,
            'message' => 'Internal server error',
        ];
    }
}

Обработка конкретных исключений

Error controller может проверять класс исключения через instanceof и возвращать разный формат ответа. Это особенно полезно для validation, access control, API errors и not found сценариев.

Air\Exception\ApiValidation
<?php

use Air\Exception\ApiValidation;

throw new ApiValidation(400, [
    'email' => 'Email already exists',
    'phone' => 'Phone is invalid',
]);
Полный пример API error controller
<?php

declare(strict_types=1);

namespace App\Module\Api\Controller;

use Air\Core\ErrorController;
use Air\Core\Front;
use Air\Exception\ApiValidation;
use Air\Exception\InvalidInput;
use Air\Exception\NotAllowed;
use Air\Form\Exception\Validation;
use Air\Log;
use Throwable;

class Error extends ErrorController
{
    public function index(): array
    {
        $exception = $this->getException();
        $request = $this->getRequest();

        $this->getView()->setLayoutEnabled(false);
        $this->getView()->setAutoRender(false);

        $this->getResponse()->setStatusCode(
            $this->resolveStatusCode($exception)
        );

        if ($exception instanceof Validation) {
            return [
                'error' => true,
                'type' => 'validation',
                'fields' => $exception->getForm()->getErrorFields(),
            ];
        }

        if ($exception instanceof ApiValidation) {
            return [
                'error' => true,
                'type' => 'api-validation',
                'fields' => $exception->getData(),
            ];
        }

        $logsConfig = Front::getInstance()->getConfig()['air']['logs'] ?? [];

        if (($logsConfig['exception'] ?? false) === true && $exception) {
            Log::error($exception->getMessage(), [
                'handler' => get_class($exception),
                'trace' => $exception->getTrace(),
                'code' => $this->getResponse()->getStatusCode(),
                'params' => [
                    'get' => $request->getGetAll(),
                    'post' => $request->getPostAll(),
                ],
            ]);
        }

        $reportErrors = Front::getInstance()->getConfig()['air']['exception'] ?? false;

        if ($reportErrors && $exception) {
            return [
                'error' => true,
                'handler' => get_class($exception),
                'message' => $exception->getMessage(),
                'trace' => $exception->getTrace(),
            ];
        }

        return [
            'error' => true,
            'message' => 'Internal server error',
        ];
    }

    private function resolveStatusCode(?Throwable $exception): int
    {
        if ($exception instanceof Validation) {
            return 400;
        }

        if ($exception instanceof ApiValidation) {
            return $exception->getCode() ?: 400;
        }

        if ($exception instanceof InvalidInput) {
            return 400;
        }

        if ($exception instanceof NotAllowed) {
            return 403;
        }

        $code = $exception?->getCode();

        if (is_int($code) && $code >= 400 && $code < 600) {
            return $code;
        }

        return 500;
    }
}

HTML error pages в UI-модуле

В UI-модуле error controller может не возвращать массив. Вместо этого он может назначить данные во view и позволить AirCMS отрендерить обычный .phtml script с layout.

app/Module/Ui/Controller/Error.php
<?php

namespace App\Module\Ui\Controller;

use Air\Core\ErrorController;

class Error extends ErrorController
{
    public function index(): void
    {
        $this->getResponse()->setStatusCode(500);
        $this->getView()->assign('exception', $this->getException());
    }
}
app/Module/Ui/View/Scripts/error/index.phtml
<section class="error-page">
    <h1>Что-то пошло не так</h1>
    <p>Попробуйте обновить страницу или вернуться позже.</p>

    <?php if ($this->exception): ?>
        <pre><?php echo htmlspecialchars($this->exception->getMessage()); ?></pre>
    <?php endif; ?>
</section>

Такой подход полезен для публичного сайта, где API-style JSON не нужен, а пользователю нужна аккуратная HTML-страница ошибки.

Встроенные исключения AirCMS

Ниже перечислены основные исключения, которые есть в ядре AirCMS. Не каждое из них нужно обрабатывать отдельно, но полезно понимать, откуда может прийти ошибка.

Core exceptions

Air\Core\Exception\ControllerClassWasNotFoundController class не найден по текущему route.
Air\Core\Exception\RouterWasNotFoundRouter не смог подобрать route.

Air\Core\Exception\StopСпециальное исключение для остановки выполнения через Front::stop().

Application/API exceptions

Stop exception

Air\Core\Exception\Stop — специальный сценарий. Если во время обработки выброшен Stop, Front выставляет status code из исключения и сразу рендерит response без запуска обычного error controller.

Остановка выполнения
<?php

use Air\Core\Front;

$this->getResponse()->setStatusCode(204);
Front::getInstance()->stop();

Практический паттерн для API

Для API-проекта обычно достаточно одного module-level error controller и нескольких специальных обработчиков внутри него: validation, api validation, access denied и fallback 500. Context-level error controller стоит добавлять только тогда, когда конкретная группа endpoints должна возвращать другой формат ошибки.

Рекомендуемый минимум: всегда обрабатывай Air\Form\Exception\Validation, Air\Exception\ApiValidation, Air\Exception\NotAllowed, валидный HTTP code из exception и fallback 500.
